01 / THE STARTING POINTFamiliar pieces. A different arrangement.

You know the work.
Why keep rebuilding
the machinery?

If you use app builders, you already think in records, rules, triggers and actions. An order arrives. Someone checks it. A price is calculated. The result goes somewhere.

Yet each application often rebuilds the same connections, hides rules inside screens, and makes a small change feel bigger than it should.

CRUD and Logic asks: can we make those pieces explicit, reusable and easy to rearrange?

FAMILIAR FOUNDATIONS / THE UNIX PIPELINE, EVOLVED

Small programs. Connected to do a bigger job.

Unix-based operating systems already let you pipe one program's output into the next program's input. Chain small programs together, and they perform a task that none of them handles alone. That compositional idea is a foundation of CRUD and Logic.

THE FAMILIAR UNIX MODEL
Read|Filter|Sort
Program output becomes the next program's input.
THE CRUD & LOGIC DIRECTION
Document→Worker→Document
Structured context moves through a business-domain pipeline.

CRUD and Logic is the next evolution of that concept: structured Documents carrying context, replaceable workers, and explicit orchestration expressed in the business's own domain and cultural language. AI can bridge a document transformation until a dedicated module is built.

It also draws on microservices, message passing, dataflow and workflow systems. The ambition is to bring these established ideas together with tighter orchestration, rather than claim the underlying idea of pipelining is new.

Cultural sensitivity is part of the design: names, dates, currencies, local conventions and the meaning of a business step must be explicit. Translation alone is not enough. The business language describes intent; the implementation language does the work. Domain compilers are planned work.

05 / THE EXECUTION LAYEROne system. Different kinds of compute.

What programming language?
As close to the metal
as the job needs.

The intent is assembly code: small, specialised modules operating close to bare metal. Some jobs could even run on bespoke PCIe devices. The architecture itself is agnostic about the language, machine or kind of processor doing the work.

COMPUTER A
Documents⇄Shared contracts
COMPUTER B

An application can span multiple computers and processor types. A worker may run on a CPU, another on a GPU or specialist device. Each implementation targets its own hardware; the document contract is what lets the pipeline connect them.

C# is used in the current prototype and proposed compiler tooling. It is a starting point, not the boundary of the system.

Destination architecture, not a list of supported devices today. Connecting different machines and processors requires compatible adapters, transport and contracts; it does not make one binary run everywhere.

08 / WHERE AI FITSTransform now. Specialise as the system matures.

A HELPING HAND FOR THE UNFINISHED PARTS.

AI can bridge
a missing module.

Then help build its replacement.

AI has two roles in the intended system. It can transform a document at a defined step while a dedicated module does not yet exist. It can also help author the focused module that eventually replaces that transformation.

The business pipeline keeps its meaning as the implementation changes.

OUTPUT CONTRACT

Continue the pipeline.

Check the resulting pages before passing them to the next worker.

This is a planned runtime capability. AI transformations can vary; they are not made deterministic by being inside a pipeline. The step needs validation, defined failure handling and review where the business requires it. A schema check alone does not prove that a transformation is correct.

BUSINESS EXCEPTIONS / A PLANNED ROLE FOR AI

People wear in shoes.
They should be able to wear in systems.

A business process describes the work we anticipated. Sometimes a person needs something done that the system was never programmed to do. That exception falls outside the process as designed, which is why systems so often refuse it. The need itself may still be valid.

The intended role for an AI module is to make that exception workable and visible: transform the document within the permitted workflow, and capture what was requested, what changed and the result. The exception becomes something people can review and learn from.

AUTHORING / LONG-TERM DIRECTION

Smaller jobs for agents.

Author, test, refactor and audit individual workers. People govern the rules and important structural decisions. Unit tests provide evidence; they are not a universal proof of correctness.

INTERFACE / DESIGNED, NOT IMPLEMENTED

Helpful local autocorrect.

A proposed small client-side model could correct names in the query box. Suggestions must resolve to known vocabulary, stay undoable, and leave uncertain text alone. The deterministic query engine still runs the request.

11 / OPEN THE HOODFor the questions behind the diagrams.

A little more architecture.
Without losing the thread.

What is inside a Document?+

A Document contains Pages for a particular business flow. The design uses XML fragments as the Page envelope, with CDATA holding the payload. That payload could be JSON, XML, SVG, G-code or text encoding of binary data.

XML metadata identifies the page and its contract. A payload still needs validation appropriate to its own format; wrapping JSON in XML does not validate its contents. File framing, indexing, encoding and version compatibility remain design questions.

How small is a worker?+

Small enough to understand and test on its own. A project rule of thumb is that a function exceeding roughly 60 lines deserves another look. The purpose is a focused responsibility, not winning a line-count contest.

Separate data access from business rules. Keep inputs, outputs and side effects explicit. The intended destination is assembly and other specialised native implementations, including bespoke hardware where useful. The system is language- and processor-agnostic; C# currently supports the prototype and proposed compiler tooling. Small units can enable specialist contributions without exposing an entire application.

How do the hand-offs work?+

The initial local runtime design calls for one long-lived process per pipeline, with small workers inside it. This describes the local execution model, not a limit on the wider application spanning machines and processor types. A new process is not launched for every document.

Memory-mapped files are the proposed local transport, with disk-backed options explored. Across machines, Homa over IP is an exploratory direction. Earlier conversations explored per-worker programs and sockets; the newer design refines that into pipeline processes. Framing, back-pressure, ordering, correlation, retries and recovery still need engineering and measurement.

Why both Git and a database?+

The proposed source of truth is the document file, versioned in Git. Postgres holds statistics and lookup information that points back to those documents. Only CRUD workers touch the database.

The aim is inspectable history alongside fast discovery. It still needs a carefully designed write path: Git history alone does not solve multi-user transactions, concurrent edits, cross-document consistency or cache invalidation. Earlier ideas included linked documents, local read caches and reviewed changes through pull requests.

How is this different from an app builder?+

The familiar part is composing a flow. The ambition goes beneath the designer: the same small workers, contracts and observable hand-offs define how the software itself is assembled.

This needs a runtime, compilers and operational tools as well as a visual interface. It is a research-led approach with real implementation costs. It has not yet demonstrated that it is faster, cheaper or simpler than existing app builders for every use case.

Where does it run, and who controls access?+

The long-term packaging preference is a configured virtual machine rather than Docker. The browser interface connects through a gateway; a desktop client is also being explored. The prototype uses Avalonia and WebAssembly with GPU-rendered drawing.

A VM is one boundary, not a complete security model. Authentication, authorisation, least-privilege worker access, signed updates, secret handling and protected observation data need explicit designs. Local communication does not make the internals automatically trustworthy.

Can an existing application be converted?+

A possible future service would analyse an application, identify focused functions and separate data access, logic and orchestration. AI could help propose that decomposition and create tests around the resulting contracts.

The discussions also explored maintenance services, reusable signed components, staged updates and a library discovered from existing code. These are commercial and research possibilities, not currently available products. Licensing, behaviour preservation and safe promotion would need checking.

What about robots and AI optimisation?+

The document idea could extend beyond orders. A robotics pipeline might transform a motion description into driver instructions while sensor documents feed defined responses. Simulation and replay could help analyse a plan before execution. No robotics safety capability is claimed.

A separate idea is AI-proposed code optimisation using C# intermediate language and a graph of known transformations. A candidate would require semantic verification and measurement before acceptance. This is future investigation, not the prototype's execution engine.
